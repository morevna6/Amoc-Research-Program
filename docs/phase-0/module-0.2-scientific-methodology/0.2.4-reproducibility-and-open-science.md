> **Publication note:** This document defines the reproducibility and open-science standards of the AMOC Research Program. These standards describe the intended direction of the programme and will be implemented progressively as datasets, code, analytical workflows, and research outputs are introduced. Not every infrastructure component described here exists at the present stage of the project.

---

## Reproducibility and Open Science

The **AMOC Research Program** is intended to produce research that can be inspected, understood, challenged, reproduced, and revised.

Publishing a result is not sufficient.

A reader should eventually be able to determine:

* which data were used;
* where those data came from;
* which version was analysed;
* how the data were transformed;
* which software and dependencies were used;
* which parameters were selected;
* how statistical or physical calculations were performed;
* how figures were generated;
* which assumptions were required;
* what uncertainty remains;
* whether the result can be regenerated.

The programme therefore treats reproducibility as part of the scientific method rather than as an optional technical feature.

Its central principle is:

> **A scientific result should preserve enough information about its evidence and computational history that another person can understand how it was produced and, where possible, reproduce it independently.**

Open science extends this principle further.

The programme should make its research process visible wherever scientific, legal, ethical, technical, and licensing conditions permit.

---

# 1. Reproducibility Is More Than Code Availability

Uploading source code does not automatically make research reproducible.

Code may still depend on:

* unavailable datasets;
* undocumented preprocessing;
* missing packages;
* unknown software versions;
* hidden notebook state;
* manually edited files;
* local directory structures;
* undocumented parameters;
* unavailable APIs;
* external services;
* unrecorded assumptions.

A repository containing code but lacking these dependencies may technically be public while remaining practically irreproducible.

The programme therefore distinguishes:

> **code availability**

from:

> **workflow reproducibility.**

---

# 2. Project Use of Reproducibility and Replication

Terminology varies across scientific disciplines.

For this programme, the following working definitions will be used.

## Reproducibility

The ability to obtain the same or sufficiently equivalent result using:

* the same underlying data;
* the documented computational methods;
* the documented analytical workflow.

## Replication

The ability to investigate the same scientific question using:

* independent data;
* independently implemented methods;
* additional observations;
* a genuinely separate analytical attempt.

Reproducibility asks:

> **Can this result be regenerated?**

Replication asks:

> **Does the scientific finding remain supported when investigated independently?**

Both are valuable.

They answer different questions.

---

# 3. Reproducibility Does Not Prove Validity

A scientifically incorrect analysis may be perfectly reproducible.

If a flawed assumption is encoded clearly in a script, another researcher may reproduce the same flawed output exactly.

Reproducibility therefore supports:

* transparency;
* verification;
* debugging;
* methodological scrutiny.

It does not by itself establish:

* physical correctness;
* causal validity;
* appropriate statistical reasoning;
* scientific truth.

The programme treats reproducibility as a necessary component of strong computational research, not as a substitute for scientific reasoning.

---

# 4. Levels of Reproducibility

Not every project output requires the same level of computational infrastructure.

The programme may use several levels.

## Level 1 — Traceable

The result records:

* source;
* methodology;
* main assumptions;
* important transformations.

## Level 2 — Reconstructable

The required analytical steps are documented sufficiently for another person to recreate the workflow.

## Level 3 — Computationally Reproducible

Code, data references, parameters, and dependencies allow the analytical output to be regenerated.

## Level 4 — Independently Reproduced

The workflow has been executed successfully from a clean or independent environment.

## Level 5 — Replicated

The underlying scientific finding has been investigated independently using separate evidence or implementation.

These levels should not be interpreted as a rigid scoring system.

They provide a vocabulary for describing the maturity of research outputs.

---

# 5. Reproducibility Begins With Provenance

Reproducibility requires knowing where evidence came from.

For each analytical dataset, the programme should eventually record:

* dataset name;
* provider;
* version;
* DOI or persistent identifier;
* download or access location;
* access date;
* licence;
* citation;
* geographic coverage;
* temporal coverage;
* variables used;
* units;
* original file format.

If an analysis cannot identify its source data precisely, later reproduction becomes unreliable.

---

# 6. Raw Data Preservation

Where technically and legally possible, raw source data should remain unchanged.

The project should distinguish among:

```text
raw
interim
processed
derived
output
```

The conceptual flow is:

> **source → raw → validated → processed → derived → analytical output**

Raw files should not be silently overwritten after:

* filtering;
* cleaning;
* interpolation;
* resampling;
* aggregation;
* unit conversion.

A transformation should create a new research object rather than erase the previous one.

---

# 7. Immutable Inputs Where Possible

Raw data should be treated as immutable inputs whenever practical.

If a source dataset itself changes because a provider publishes a new version, the programme should record:

* previous version;
* new version;
* date of change;
* reason for updating;
* analyses potentially affected.

Replacing an input without recording the change can make previous results impossible to reproduce.

---

# 8. Data Versioning

Scientific datasets may evolve.

New versions may contain:

* additional observations;
* corrected measurements;
* revised calibration;
* changed quality flags;
* new metadata;
* altered processing.

Analyses should therefore refer to specific dataset versions whenever possible.

A statement such as:

> “RAPID data were used”

is eventually insufficient.

A reproducible analysis should identify the exact data release used.

---

# 9. File Integrity

For important downloaded inputs, the programme may eventually record file-integrity information such as:

* file size;
* checksum;
* modification date;
* source version.

Checksums may be especially useful when:

* files are large;
* upstream sources can change;
* archival consistency matters.

The goal is to ensure that two files with the same name are not automatically assumed to contain the same data.

---

# 10. Data Manifests

As dataset use expands, the programme may maintain data manifests containing:

* local filename;
* upstream filename;
* source;
* version;
* checksum;
* access date;
* licence;
* processing status;
* related analyses.

A data manifest can provide a machine-readable connection between external scientific data and internal project workflows.

---

# 11. Transformation Provenance

Every important processed dataset should be traceable to:

* its original source;
* the script that generated it;
* transformation parameters;
* software environment;
* previous processing stage.

The desired chain is:

> **processed dataset → processing script → raw dataset → external source**

This prevents processed files from becoming orphaned research objects whose origins are eventually forgotten.

---

# 12. Manual Data Editing

Manual changes to analytical data should be avoided where practical.

Examples include:

* deleting rows in a spreadsheet;
* manually replacing values;
* copy-pasting filtered data;
* editing timestamps by hand.

Such operations are difficult to reproduce reliably.

Where a manual intervention is unavoidable, it should be documented explicitly.

Prefer:

> **raw data + transformation script**

over:

> **mysteriously corrected final.csv**

The latter is efficient only until everyone forgets what happened.

---

# 13. Reproducible Data Cleaning

Cleaning rules should be implemented as explicit transformations where possible.

Examples include:

* missing-value handling;
* quality-flag filtering;
* timestamp conversion;
* coordinate transformation;
* duplicate removal;
* unit conversion;
* invalid-value exclusion.

A cleaning decision should answer:

1. What condition triggered the change?
2. What action was performed?
3. Why was that action scientifically justified?
4. How many observations were affected?

---

# 14. Computational Environments

Analytical code depends on software environments.

The programme should eventually document:

* programming-language version;
* package versions;
* system dependencies where relevant;
* environment configuration;
* major external tools.

Possible environment records may include:

* `requirements.txt`;
* `pyproject.toml`;
* environment lock files;
* `environment.yml`;
* container definitions where justified.

The exact technology may evolve.

The requirement is not loyalty to one packaging system.

The requirement is dependency traceability.

---

# 15. Dependency Pinning

Package behaviour may change between software versions.

An analysis that works with one version may:

* fail;
* produce warnings;
* change numerical behaviour;
* alter defaults;

under another.

Important research releases should therefore record sufficiently precise dependency information for reproduction.

---

# 16. Computational Environment Versus Research Environment

Reproducing computation may require more than software packages.

Relevant environmental information may sometimes include:

* operating system;
* CPU architecture;
* GPU environment;
* numerical libraries;
* parallelisation;
* hardware-specific dependencies.

Most analyses will not require all of these.

They should be documented when they materially affect results.

---

# 17. Randomness

Statistical and machine-learning workflows may involve randomness.

Examples include:

* sampling;
* train-test splitting;
* bootstrapping;
* stochastic optimisation;
* random initialisation.

Where appropriate, the programme should record random seeds.

However, setting a seed does not always guarantee identical results across:

* hardware;
* library versions;
* parallel-processing systems.

Where exact reproducibility cannot be guaranteed, the expected degree of variation should be documented.

---

# 18. Deterministic and Statistical Reproducibility

Some results can reasonably be expected to reproduce exactly.

Examples include deterministic calculations performed with identical inputs and software.

Other results may reproduce statistically rather than bit-for-bit.

For stochastic models, the important requirement may be that:

* distributions;
* uncertainty estimates;
* qualitative conclusions;
* performance ranges;

remain consistent.

The programme should specify what kind of reproduction is expected.

---

# 19. Notebooks

Jupyter notebooks can be highly valuable for:

* exploration;
* learning;
* visualisation;
* research notes;
* prototype analysis.

However, notebooks also create reproducibility risks.

These include:

* hidden execution state;
* cells run out of order;
* manually modified variables;
* incomplete dependency information;
* embedded outputs inconsistent with code.

Important notebooks should therefore eventually be tested from a clean kernel and executed sequentially.

---

# 20. Notebook State

A notebook is reproducible only when its visible cell order is capable of generating its outputs.

The programme should avoid relying on variables created through previous hidden execution history.

Before publication of an important notebook:

1. restart the environment;
2. clear or regenerate outputs where appropriate;
3. run cells sequentially;
4. verify that results are reproduced.

---

# 21. Exploration Versus Production Workflows

Exploratory notebooks are allowed to be messy.

Research requires experimentation.

However, once an analysis becomes a formal project result, important logic should increasingly move toward:

* reusable functions;
* scripts;
* modules;
* documented configuration;
* tested workflows.

The programme should distinguish:

> **research sandbox**

from:

> **reproducible research pipeline.**

Not every experiment needs production engineering.

Formal findings deserve stronger structure.

---

# 22. Separation of Code and Configuration

Parameters that materially affect analytical results should be identifiable.

These may include:

* time window;
* geographic boundaries;
* baseline period;
* thresholds;
* smoothing parameters;
* model settings;
* variable selections.

Where practical, such parameters should be separated from hidden implementation logic.

This makes analytical assumptions easier to inspect.

---

# 23. Reproducible Figures

Important scientific figures should be generated from code whenever possible.

A formal figure should ideally be traceable to:

* source dataset;
* processing workflow;
* plotting code;
* configuration;
* figure version.

Manual post-processing of figures should be minimised.

If manual editing materially changes scientific content, it should be documented.

---

# 24. Figure Provenance

A figure should not become detached from the analysis that created it.

Future documentation may record:

* Figure ID
* source script
* source data
* variables
* analysis version
* caption
* publication location

This will become increasingly useful as the programme produces many figures across research phases.

---

# 25. Tables and Numerical Results

Important tables and summary statistics should also be generated programmatically where practical.

Manual transcription can introduce:

* rounding inconsistencies;
* copy errors;
* outdated values;
* mismatches between analysis and publication.

The preferred flow is:

> **analysis → generated output → publication**

rather than:

> **analysis → manual copying → manual editing → publication**

---

# 26. Reproduction From a Clean Environment

Before an important analytical output is considered mature, the programme should eventually attempt reproduction from a clean environment.

The test should answer:

> **Can the documented project state recreate the output without relying on hidden local knowledge?**

A possible procedure is:

1. obtain the project version;
2. recreate dependencies;
3. acquire documented source data;
4. execute preprocessing;
5. execute analysis;
6. regenerate figures or tables;
7. compare outputs.

Failures should reveal missing parts of the reproducibility chain.

---

# 27. Reproducibility Failures Are Useful

A failed reproduction attempt may reveal:

* undocumented dependency;
* hidden manual step;
* missing data;
* unstable software;
* incorrect path assumption;
* obsolete API;
* random behaviour;
* code defect.

Such failures should be treated as diagnostic information.

They are preferable to discovering years later that an important result cannot be reconstructed.

---

# 28. Automated Checks

As computational complexity grows, some reproducibility checks may eventually be automated.

Potential checks include:

* import tests;
* schema validation;
* unit tests;
* data-integrity tests;
* figure-generation tests;
* pipeline execution;
* dependency checks.

Automation should be introduced where it provides meaningful reliability rather than administrative complexity for its own sake.

---

# 29. Continuous Integration

If the project develops substantial reusable software, continuous integration may eventually be used to test:

* code execution;
* tests;
* data-independent workflows;
* formatting or validation;
* environment compatibility.

Large scientific datasets may make complete automated pipeline reproduction impractical.

The project should distinguish between what can reasonably be automated and what requires manual scientific review.

---

# 30. Open Science

Open science means making the scientific process more accessible, inspectable, reusable, and collaborative where appropriate.

For this programme, open science may include:

* public research documents;
* transparent methodology;
* public code;
* source attribution;
* data provenance;
* reproducible workflows;
* open issue tracking;
* documented corrections;
* reusable educational material;
* accessible scientific communication.

Open science does not mean that every object must always be publicly redistributed.

---

# 31. Open by Default, Restricted by Reason

Where possible, project-generated materials should be open.

Exceptions may arise because of:

* third-party licences;
* restricted datasets;
* privacy;
* ethical concerns;
* intellectual-property restrictions;
* security concerns;
* technical limitations;
* very large file sizes.

When material cannot be shared, the programme should still document:

* what the material is;
* where it can be obtained;
* why redistribution is restricted;
* how it was used.

---

# 32. FAIR Principles

The programme may use the **FAIR principles** as guidance for research data and computational resources.

FAIR refers to making research objects:

* **Findable**
* **Accessible**
* **Interoperable**
* **Reusable**

FAIR does not mean that all data must be openly downloadable without restriction.

A restricted dataset can still be documented in ways that improve findability, metadata quality, interoperability, and reuse.

The programme will therefore distinguish:

> **FAIR**

from:

> **open.**

They overlap but are not identical concepts.

---

# 33. Findability

Research objects should become increasingly easy to locate.

Possible practices include:

* predictable directory structures;
* descriptive filenames;
* identifiers;
* metadata;
* indexes;
* manifests;
* documentation links;
* searchable literature records.

A scientifically valuable result is less useful when nobody can determine where it came from.

---

# 34. Accessibility

Where legal and technical conditions permit, research outputs should be accessible.

This may involve:

* public repository files;
* persistent archives;
* documented download procedures;
* source links;
* data-access instructions.

Accessibility also requires documentation.

A file that can be downloaded but cannot be understood is only partially accessible.

---

# 35. Interoperability

Data and research objects should use standard or well-documented formats where practical.

Potential considerations include:

* recognised units;
* standard timestamps;
* geographic coordinates;
* structured metadata;
* established scientific formats.

Scientific datasets may use formats such as:

* NetCDF;
* CSV;
* HDF;
* Zarr;
* other domain-appropriate standards.

The programme will select formats according to scientific suitability rather than convenience alone.

---

# 36. Reusability

A reusable research object requires enough context to understand:

* what it contains;
* how it was produced;
* which licence applies;
* how it should be cited;
* what assumptions it contains;
* what limitations apply.

Data without metadata have limited reuse value.

Code without documentation has the same problem wearing a different costume.

---

# 37. Metadata as Research Infrastructure

Metadata should be treated as part of the data.

Relevant metadata may describe:

* variable definitions;
* units;
* coordinates;
* quality flags;
* measurement systems;
* temporal coverage;
* spatial coverage;
* processing level;
* version;
* provider;
* licence.

Loss of metadata can make scientifically valid data impossible to interpret correctly.

---

# 38. Open Code

Where appropriate, analytical code should be publicly inspectable.

Open code allows others to examine:

* transformations;
* assumptions;
* implementation;
* statistical methods;
* physical calculations.

However, public availability does not guarantee:

* correctness;
* readability;
* reproducibility;
* scientific validity.

The programme should therefore combine open code with documentation and verification.

---

# 39. Code Documentation

Important scientific code should explain:

* inputs;
* outputs;
* units;
* assumptions;
* important parameters;
* expected behaviour.

Documentation is especially important for physical calculations where a mathematically correct-looking function may still use the wrong scientific convention.

---

# 40. Code Reuse

Reusable code should increasingly be separated from analysis-specific logic.

Potential reusable components may include:

* data loaders;
* validation functions;
* transformation utilities;
* oceanographic calculations;
* time-series tools;
* plotting utilities.

Reuse can improve consistency.

However, abstraction should not obscure scientific meaning.

---

# 41. Testing Scientific Code

Testing scientific code may include several levels.

### Unit Tests

Verify individual functions.

### Integration Tests

Verify that components work together.

### Scientific Validation Tests

Verify results against:

* known analytical solutions;
* published examples;
* reference implementations;
* accepted physical ranges.

A function returning a number without crashing is not sufficient evidence that the number is scientifically correct.

---

# 42. Reference Implementations

Where physical calculations have established reference libraries or documented standards, project implementations should be compared against them when possible.

For example, future seawater thermodynamic calculations should use or validate against accepted oceanographic standards rather than casually reproducing complex equations from memory.

This reduces unnecessary implementation risk.

---

# 43. Reproducible Statistical Analysis

Statistical workflows should record:

* analytical period;
* preprocessing;
* model specification;
* parameters;
* statistical assumptions;
* significance criteria where relevant;
* uncertainty method;
* software implementation.

Sensitivity analyses should also remain reproducible.

---

# 44. Reproducible Machine Learning

If machine learning is later introduced, reproducibility should include:

* dataset version;
* feature construction;
* data splitting;
* random seeds;
* preprocessing;
* hyperparameters;
* model architecture;
* software versions;
* evaluation metrics;
* baseline models.

A saved model without this information provides limited scientific traceability.

---

# 45. Model Artefacts

Where useful and feasible, future model outputs may include:

* trained parameters;
* configurations;
* evaluation summaries;
* run metadata;
* experiment identifiers.

Large model artefacts may require external storage.

The repository should then maintain links and metadata rather than pretending Git is an ocean-sized storage system.

---

# 46. External APIs and Services

Some workflows may depend on:

* APIs;
* remote archives;
* cloud services;
* data portals.

These systems can change.

The programme should record:

* endpoint or service;
* access date;
* query parameters;
* relevant API version;
* retrieved dataset version.

Where practical, retrieved raw responses or files should be preserved according to licensing conditions.

---

# 47. External Link Decay

Scientific URLs may disappear or change.

Where possible, the programme should prefer:

* DOIs;
* persistent identifiers;
* official archives;
* versioned releases.

Ordinary URLs may still be necessary.

Their potential instability should be recognised.

---

# 48. Persistent Identifiers

Persistent identifiers can improve traceability.

Examples include:

* DOI;
* dataset accession number;
* release tag;
* archival identifier.

As the programme matures, formal releases may eventually use persistent archival services where useful.

---

# 49. Releases and Research Milestones

Git commits document detailed project evolution.

Major research milestones may require clearer releases.

A release may eventually identify:

* research-document versions;
* code version;
* dataset versions;
* analytical outputs;
* known limitations.

This can make historical reproduction easier than relying on the latest branch alone.

---

# 50. Version Control

Detailed version-control policy will be defined in:

For reproducibility purposes, the essential principle is:

> **The exact project state associated with an important result should be identifiable.**

This may involve:

* commits;

* document versions.

# 51. Reproducible Research Reports

A formal analytical report should eventually identify, where relevant:

* research question;
* source data;
* data versions;
* methodology;
* software environment;
* code location;
* figure-generation process;
* assumptions;
* uncertainty;
* limitations;
* project version.

The report should function as an entry point into the reproducibility chain.

---

# 52. Data Availability Statements

Future research outputs may include a data-availability statement describing:

* datasets used;
* providers;
* access conditions;
* licences;
* versions;
* restrictions.

This is particularly important when source data cannot be redistributed through the project repository.

---

# 53. Code Availability Statements

Formal analytical outputs may similarly identify:

* code location;
* release or commit;
* environment instructions;
* relevant workflow.

The phrase:

> “Code available on GitHub”

should eventually be replaced by something precise enough to reproduce the actual published analysis.

---

# 54. Licensing

Open science requires respect for intellectual-property and licensing conditions.

The project should distinguish among:

* project-generated code;
* project-generated written content;
* external datasets;
* third-party figures;
* scientific publications;
* software dependencies.

Public availability does not eliminate copyright or licence requirements.

---

# 55. Dataset Redistribution

Some datasets may permit redistribution.

Others may require users to obtain the data directly from the provider.

The project should never redistribute external scientific data merely because downloading it was easy.

Licence terms should determine what can be shared.

---

# 56. Citation and Attribution

Reusable research requires attribution.

The programme should credit:

* dataset creators;
* observing programmes;
* scientific authors;
* software projects;
* external methods.

Citation is not a bureaucratic decoration.

It preserves the intellectual and technical provenance of the research.

Detailed citation standards will be defined in `0.2.6`.

---

# 57. Open Access and Scientific Quality

Open access improves availability.

It does not guarantee scientific quality.

Likewise, paywalled research is not automatically lower quality.

Evidence evaluation should remain separate from access conditions.

The programme should prefer legally accessible sources when possible while judging scientific evidence according to methodological relevance and quality.

---

# 58. Open Science and Negative Results

Open research practice should permit publication of:

* null results;
* failed reproductions;
* methodological failures;
* sensitivity problems;
* inconclusive findings.

A project that exposes only successful analyses creates an incomplete record of the research process.

---

# 59. Open Corrections

Errors should be corrected transparently.

A correction should identify:

* what was wrong;
* which outputs were affected;
* what changed;
* whether conclusions changed.

The programme should not silently replace scientifically meaningful errors when a visible correction provides a more accurate research history.

---

# 60. Reproducibility and Scientific Disagreement

Reproducibility does not eliminate disagreement.

Two reproducible analyses may disagree because they use:

* different datasets;
* different assumptions;
* different statistical models;
* different physical definitions.

Reproducibility makes those differences easier to investigate.

That is part of its scientific value.

---

# 61. Reproducing External Research

The programme may later reproduce published AMOC studies.

Such reproduction should record:

* target paper;
* original dataset;
* original method;
* implementation differences;
* unavailable information;
* reproduced outputs;
* discrepancies.

A failed reproduction does not automatically prove the original paper wrong.

Possible explanations must first be investigated.

---

# 62. Replication

Replication goes beyond recreating the original analysis.

A replication may test whether a finding remains supported using:

* updated observations;
* another observing system;
* an independent reconstruction;
* different but defensible methodology.

Replication can provide evidence about robustness beyond the original implementation.

---

# 63. Reproduction Before Extension

Where the programme intends to extend a published method, reproducing the original approach first may be valuable.

The sequence may be:

> **understand → reproduce → validate → modify → compare**

This helps separate:

* failure to understand the original method;

from:

* genuine effects of the new modification.

---

# 64. Reproducibility Checkpoints

Major investigations may eventually include checkpoints after:

### Data Acquisition

Can the source data be obtained again?

### Processing

Can processed data be regenerated?

### Analysis

Can analytical results be recreated?

### Visualisation

Can figures be regenerated?

### Publication

Does the published claim correspond to the reproducible output?

These checkpoints create multiple opportunities to detect hidden dependencies.

---

# 65. Minimum Reproducibility Record

Before a major computational result is published, the programme should normally be able to identify:

1. **Research question**
2. **Dataset**
3. **Dataset version**
4. **Source**
5. **Raw-data provenance**
6. **Processing code**
7. **Analytical code**
8. **Important parameters**
9. **Software environment**
10. **Randomness controls where relevant**
11. **Output-generation method**
12. **Project version**
13. **Known reproducibility limitations**

If several of these elements are missing, the result should not be described as fully reproducible.

# 68. Reproducibility Status

Research outputs may eventually receive reproducibility labels such as:

### Not Applicable

No computational workflow involved.

### Documented

Methods and sources described.

### Partially Reproducible

Some necessary materials or dependencies unavailable.

### Reproducible

Workflow successfully regenerates the main result.

### Independently Reproduced

Result regenerated through an independent environment or implementation.

### Replicated

Finding supported through an independent research attempt.

These labels should describe actual verification performed, not aspiration.

---

# 69. Known Limitations of Reproducibility

Perfect reproduction may not always be possible.

Potential causes include:

* evolving external datasets;
* inaccessible historical versions;
* unavailable proprietary data;
* discontinued APIs;
* numerical differences;
* software obsolescence;
* external-service changes;
* hardware dependencies.

The programme should document these limitations rather than pretending they do not exist.

---

# 70. Archival Strategy

As the project matures, important research states may eventually be archived separately from the active repository.

An archive may preserve:

* released code;
* research documents;
* environment information;
* metadata;
* derived outputs;
* citation information.

Archival practice will be developed when the project begins producing analytical releases that require long-term preservation.

---

# 71. Open Science Does Not Mean Premature Publication

Transparency does not require publishing every unfinished thought as a scientific result.

The programme may contain:

* exploratory work;
* incomplete calculations;
* draft hypotheses;
* failed code;
* early notes.

These should be labelled appropriately.

Open science should make the research process visible without confusing preliminary work with validated findings.

---

# 72. Status Labels Matter

Research objects should increasingly indicate whether they are:

* planned;
* exploratory;
* draft;
* validated;
* published;
* revised;
* superseded.

This reduces the risk that readers interpret an unfinished notebook as a formal scientific conclusion merely because it exists publicly.

---

# 73. Open Communication

Public-facing material should link back to the reproducible research record when available.

The relationship should be:

> **public explanation → technical interpretation → analytical result → methodology → evidence**

This ensures that simplified communication still has a route back to full scientific detail.

---

# 74. Reproducibility as Memory

Reproducibility is valuable not only for other researchers.

It protects the project from its own future forgetfulness.

A workflow documented today may be revisited:

* months;
* years;
* many project phases;

later.

Documentation should therefore be written with the assumption that future understanding cannot depend on remembering what the author once had open on a laptop.

---

# 75. Open Science as Accountability

Open research allows readers to challenge:

* assumptions;
* methods;
* code;
* interpretations.

This may expose mistakes.

That is a feature rather than a failure.

A research process that can be challenged can also be improved.

---

# 76. Programme Reproducibility Principle

The programme’s reproducibility principle can be summarised as:

> **Every important computational result should preserve a traceable path from its published claim back through interpretation, analysis, code, transformations, data, and original source.**

---

# 77. Programme Open-Science Principle

The programme’s open-science principle is:

> **Research should be as open as reasonably possible and as restricted as scientifically, legally, or ethically necessary.**

Openness should support:

* verification;
* learning;
* reuse;
* collaboration;
* accountability.

It should not override legitimate constraints.

# 78. Relationship to Research Workflow

[`0.2.1 — Research Workflow`](0.2.1-research-workflow.md) established the programme-wide research sequence.

Reproducibility operates throughout that sequence:

> **Question → Evidence → Data → Transformation → Analysis → Interpretation → Publication → Reassessment**

Each transition should leave enough information for the previous stage to be reconstructed.

# 79. Relationship to Evidence Evaluation

[`0.2.2 — Evidence Hierarchy and Evaluation`](0.2.2-evidence-hierarchy-and-evaluation.md) established how scientific evidence should be evaluated.

Reproducibility contributes to evidence evaluation because transparent methods make it easier to inspect:

* assumptions;
* calculations;
* uncertainty;
* methodological sensitivity.

However, reproducibility is only one dimension of evidence quality.

---

# 80. Relationship to Scientific Reasoning

[`0.2.3 — Scientific Reasoning`](0.2.3-scientific-reasoning.md) established how the programme should move from evidence toward conclusions.

Reproducibility makes that reasoning chain inspectable.

The desired relationship is:

> **question → evidence → method → result → reasoning → claim**

A reader should eventually be able to inspect every major link.

# 81. Relationship to Version Control

The next document:

> **0.2.5 — Version Control and Research Change Management**

will define how the programme preserves changes to:

* research documents;

Version control therefore provides the historical dimension of reproducible research.

## Closing Statement

Reproducibility is not an administrative burden added after scientific work.

It is part of what makes computational scientific work inspectable.

Open science extends that principle by making the research process available for:

* scrutiny;
* learning;
* reuse;
* correction;
* collaboration.

The AMOC Research Program therefore aims to build research that does not merely produce results.

It should preserve the path that produced them.

Years from now, a result should not depend on somebody remembering:

> “I think this notebook used the second CSV, after I fixed something manually.”

Civilisation has suffered enough from `final_v2_REAL_final.csv`.
